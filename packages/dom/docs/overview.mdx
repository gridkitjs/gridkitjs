title: "Overview"
description: "Framework-free browser behaviours for GridKit renderers: gestures, focus, observers, virtualization, overlays, menus, toolbars and announcements."
---

@gridkitjs/dom holds every browser behaviour a grid needs that is not drawing: pointer gestures, keyboard focus movement, the observers behind fit-to-width and infinite scroll, the row virtualizer's measuring, overlays and the menus shown in them, toolbars, and the live region it reports changes through. @gridkitjs/core decides what the grid does and runs without a DOM; @gridkitjs/dom does what needs one, with no framework; a renderer such as @gridkitjs/react draws the markup and attaches these behaviours to it. A second renderer — for Angular, Vue or Svelte — reuses both unchanged.

You only need this package to write a renderer of your own. @gridkitjs/react depends on it already, so installing that is enough to use the grid.

## Install

```ts
npm install @gridkitjs/dom
```

## The contract

Every behaviour is attached to elements the renderer already drew and handed options, owns its own listeners and observers, reports through callbacks, and gives back the way to end it — a function, or an object with `detach` or `destroy`. None names a framework's types, so each maps onto a framework's own lifecycle: a React ref callback or effect, an Angular directive and `ngOnDestroy`, a Vue `onMounted`, a Svelte action.

```ts
const detach = observeElementWidth(element, (width) => {
  /* … */
});
// later, when the element goes away:
detach();
```

Where a behaviour reads the grid's markup, it relies on the attributes @gridkitjs/react renders — `data-gridkit-column` on header and body cells, `data-gridkit-row-index` on body rows, `data-gridkit-group-by-bar` and `data-gridkit-group-chip` on the group-by bar — so a renderer that draws the same markup gets the same behaviour. What a behaviour reports that changes how the grid looks — a drop target, the window of rows, the focused cell — is the renderer's to draw; what changes the grid's state goes through the controller's actions.

## Body event targets

A renderer keeps its rows cheap to re-render by handling the body's clicks, focus and keys with one listener on the `<tbody>` rather than one per cell. These turn such an event's `target` into what it addresses in the grid's markup, `null` when it addresses none:

| Function               | Returns                                                                                                                                       |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `bodyCellFrom(target)` | `{ rowIndex, columnIndex, columnId }` — the data cell (`td[data-gridkit-column]`) it is in. Never a group header's cell, which has no column. |
| `groupRowFrom(target)` | `{ rowIndex, groupId }` — the group-header row (`tr[data-gridkit-group]`) it is in.                                                           |
| `bodyRowFrom(target)`  | `{ rowIndex, columnId }` — any body row it is in, with the column of its cell in that row, or `null` for none — what a row click reports.     |

`rowIndex` is the row's place among every body row, read off its `data-gridkit-row-index`, so it holds under virtualization, where a row's place in the DOM does not.

```ts
import { bodyCellFrom } from "@gridkitjs/dom";

tbody.addEventListener("click", (event) => {
  const cell = bodyCellFrom(event.target);
  if (cell !== null) select(view.pageRows[cell.rowIndex], cell.columnId);
});
```

## Live announcer

`createLiveAnnouncer(container?)` adds one visually hidden live region (`role="status"`, `aria-live="polite"`) as the last child of `container` — `document.body` when omitted — and returns `announce(text)` and `destroy()`. The region carries the `gridkit-sr-only` class, which @gridkitjs/theme-tailwind clips to nothing while keeping it in the accessibility tree.

```ts
import { createLiveAnnouncer } from "@gridkitjs/dom";

const announcer = createLiveAnnouncer(gridElement);
announcer.announce("Amount, column 2 of 5");
announcer.announce("Amount, column 2 of 5"); // read out again
announcer.destroy();
```

A live region speaks only when its text changes, so `announce` makes a repeat of the last message a change of its own: the same text twice in a row is read twice.

## Element width

`observeElementWidth(element, onWidth)` reports `element.clientWidth` straight away and again whenever it changes, and returns the function that stops it — the width `resizeMode: "fit"` fills, passed to the controller as `viewportWidth`. The first report is synchronous, so columns laid out before paint never show at the wrong width for a frame.

```ts
import { observeElementWidth } from "@gridkitjs/dom";

const disconnect = observeElementWidth(viewportElement, (width) => {
  controller.setOptions({ ...options, viewportWidth: width });
});
```

## Gestures

A gesture starts from a `PointerPress` — the `pointerdown` that began it, native or a framework's wrapper around one — and only from the main button of the primary pointer: a right-click or a second finger starts nothing, and the starter returns `false`. While it runs, the pointer is captured, so the gesture keeps reporting wherever the pointer goes, and <Kbd>Escape</Kbd> cancels it.

### Column resize

`startColumnResizeGesture(handle, press, session, { onMove, onEnd, onCancel })` drags a column's edge. `session` comes from @gridkitjs/core's `beginColumnResize`, which also turns each pointer position into a clamped width. `onMove(width)` reports every move; `onEnd(width)` reports the release, with `null` when the width ended where it started — a click on the handle is not a resize; `onCancel()` reports <Kbd>Escape</Kbd> or a cancelled pointer.

```ts
import { beginColumnResize } from "@gridkitjs/core";
import { startColumnResizeGesture } from "@gridkitjs/dom";

handle.addEventListener("pointerdown", (event) => {
  const session = beginColumnResize(column, width, event.clientX);
  startColumnResizeGesture(handle, event, session, {
    onMove: (width) => controller.resizeColumn(session.columnId, width, "move"),
    onEnd: (width) => {
      if (width !== null)
        controller.resizeColumn(session.columnId, width, "end");
    },
    onCancel: () =>
      controller.cancelColumnResize(
        session.columnId,
        startSizing,
        session.startWidth,
      ),
  });
});
```

`measureColumnContent(table, columnId)` is the width the widest rendered cell of a column needs to show its content in full — what double-clicking a resize handle sizes it to, through `sizeColumnToContent` — or `null` when the column has no cells.

### Drag to reorder

`startDragReorder(id, grabElement, press, { resolveTarget, onState, onDrop })` is the gesture behind every reorder in the grid — a header dragged among the others or into the group-by bar, a group-by chip dragged within it. Nothing is reported until the pointer has travelled 4 pixels, so a press that stays put remains a click; from then on every move asks `resolveTarget(clientX, clientY, id)` where a drop would land and reports `onState({ draggedId, dropTarget, ghostTransform })` — what to draw, with `ghostTransform` a CSS `transform` keeping the ghost under the pointer where it was picked up. Release over a target calls `onDrop(target, id)`; every ending reports `onState(NO_DRAG)`.

```ts
import {
  NO_DRAG,
  resolveColumnDropTarget,
  startDragReorder,
} from "@gridkitjs/dom";

header.addEventListener("pointerdown", (event) => {
  startDragReorder(columnId, header, event, {
    resolveTarget: (x, y, id) =>
      resolveColumnDropTarget(x, y, id, {
        order,
        groupBy,
        groupByDraggableIds,
      }),
    onState: (state) => draw(state),
    onDrop: (target, id) =>
      target.kind === "group-by"
        ? controller.moveGroupBy(id, target.beforeColumnId)
        : controller.moveColumn(id, target.beforeId),
  });
});
```

The grid's own targets are hit-tested against its markup:

| Function                                           | Returns                                                                                                                                                                                            |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `resolveColumnDropTarget(x, y, movedId, context)`  | `{ kind: "column-order", beforeId }` over another `th[data-gridkit-column]`, by which half the pointer is in; else a group-by target for a column that may be grouped and is not yet; else `null`. |
| `resolveGroupByDropTarget(x, y, movedId, groupBy)` | `{ kind: "group-by", beforeColumnId }` over `[data-gridkit-group-by-bar]`, before or after the `[data-gridkit-group-chip]` under the pointer, or appended; `null` elsewhere.                       |

Either returns `null` for a drop that would change nothing, so a drop indicator only ever promises a move that happens.

## Focus movement

A grid is one tab stop: <Kbd>Tab</Kbd> reaches it and passes it by, and the arrow keys, <Kbd>Home</Kbd>, <Kbd>End</Kbd>, <Kbd>PageUp</Kbd> and <Kbd>PageDown</Kbd> move within it. `createGridFocus({ rowCount, columnCount, isSkippableRow, virtualRange })` keeps that tab stop — starting on the header's first cell — and moves the browser's focus with it.

| Member                                 | Description                                                                                                                                   |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `getFocus()`                           | The focused cell, `{ rowIndex, columnIndex }` with `HEADER_ROW` (`-1`) for the header, clamped to the counts. The same object until it moves. |
| `subscribe(listener)`                  | Calls `listener` when the focused cell moves.                                                                                                 |
| `setOptions(options)`                  | The current counts, skippable rows and virtualized window, given on every render. Calls no listener.                                          |
| `attach({ getHeaderRow, getBodyRow })` | Connects it to the rendered rows; returns the function that disconnects them.                                                                 |
| `focusCell(rowIndex, columnIndex)`     | Moves the tab stop. Moving to the focused cell does nothing.                                                                                  |
| `handleKey(key, modifiers, pageSize)`  | Moves the tab stop as a navigation key does, and returns `true` — prevent the key's default then — or returns `false` for any other key.      |
| `focusDrawnCell(drawn)`                | Called after drawing `drawn`, a value `getFocus()` returned: moves the browser's focus to that cell if a move to it is pending.               |

```ts
import { HEADER_ROW } from "@gridkitjs/core";
import { createGridFocus, findBodyRow, measurePageSize } from "@gridkitjs/dom";

const focus = createGridFocus({ rowCount, columnCount });
focus.attach({
  getHeaderRow: () => headerTable.tHead?.rows[0] ?? null,
  getBodyRow: (rowIndex) => findBodyRow(bodyTable, rowIndex),
});
focus.subscribe(() => draw()); // draw() renders tabindex 0 on focus.getFocus(), then calls focus.focusDrawnCell(focus.getFocus())

grid.addEventListener("keydown", (event) => {
  if (focus.handleKey(event.key, event, measurePageSize(bodyTable))) {
    event.preventDefault();
  }
});
```

The browser's focus follows only once the move is drawn, so it lands on the cell in the new markup — after a column moves, the header now at that index. A virtualized row outside the drawn window is scrolled into it with `virtualRange.scrollToIndex` and focused when a later drawing mounts it. `findBodyRow(bodyTable, rowIndex)` finds a body row by its `data-gridkit-row-index`, not its position, which under virtualization is off by the rows not mounted; `measurePageSize(bodyTable)` is how many rows a page key moves — as many as fit the body's scrolling area.

## Row virtualizer

`createRowVirtualizer(scrollElement, { estimatedRowHeight, overscan, onRange })` windows a long list of rows inside a scrolling element down to those near its scroll position. It measures each rendered row's real height — rows need not be uniform — and reports the window to render through `onRange({ startIndex, endIndex, offsetBefore, offsetAfter })`, with `offsetBefore`/`offsetAfter` the heights of the spacers that stand in for the rows outside it. It reports only when the window moves.

| Member                          | Description                                                                                                                |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `setRowCount(count)`            | How many rows there are. Heights measured for rows that remain are kept.                                                   |
| `resetHeights()`                | Forgets every measured height — after a sort or filter, when the rows at each index are different rows.                    |
| `measureRow(index)`             | A ref callback for row `index`'s element, measuring it while mounted. The same function for the same index every time.     |
| `scrollToIndex(index, options)` | Scrolls a mounted row into view; jumps to an unmounted one's estimated offset, then scrolls to it properly once it mounts. |
| `destroy()`                     | Stops listening and measuring.                                                                                             |

```ts
import { createRowVirtualizer } from "@gridkitjs/dom";

const virtualizer = createRowVirtualizer(bodyElement, {
  estimatedRowHeight: 40,
  overscan: 4,
  onRange: (range) => drawRows(range), // rows startIndex..endIndex, between two spacers
});
virtualizer.setRowCount(rows.length);

// while drawing row `index`:
virtualizer.measureRow(index)(rowElement);
```

The arithmetic is @gridkitjs/core's `visibleRange`; this owns the measured heights, the scroll and resize listeners, and one `ResizeObserver` for every mounted row.

## Infinite scroll

`attachInfiniteScroll(root, options)` calls `onLoadMore` as a sentinel element — the last row of the body — comes within `rootMargin` of the scrolling `root`, at most once until `isLoadingMore` has gone from `true` back to `false`. It returns `update(options)`, which a renderer calls after every render with the current options and sentinel (the sentinel comes and goes with `hasMore`), and `detach()`.

```ts
import { attachInfiniteScroll } from "@gridkitjs/dom";

const scroll = attachInfiniteScroll(bodyElement, {
  sentinel: lastRow,
  hasMore: true,
  onLoadMore: () => fetchNextPage(),
});

// after each render
scroll.update({ sentinel: lastRow, hasMore, isLoadingMore, onLoadMore });
scroll.detach();
```

When a load finishes but the rows it appended leave the sentinel still in range, the next load starts straight away — nothing would scroll it out and back in to trigger one. With `hasMore` false or no sentinel, nothing is observed.

## Overlay

`attachOverlay(anchor, panel, options)` shows a panel the renderer has already put in the page — a menu, a popover, a filter editor, usually rendered into `document.body` so no scrolling ancestor clips it — beside `anchor`, an element or an `{ x, y }` point, and returns the function that ends it.

```ts
import { attachOverlay } from "@gridkitjs/dom";

const detach = attachOverlay(headerCell, menuElement, {
  placement: "bottom-start",
  gap: 4,
  onDismiss: (reason) => closeMenu(), // removes menuElement, then calls detach()
});
```

| Option          | Type                                                        | Description                                                                                                    |
| --------------- | ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `placement`     | `"bottom-start"`, `"top-end"`, `"right-start"` and the rest | Where the panel would rather open. Defaults to `"bottom-start"`.                                               |
| `gap`           | `number`                                                    | Pixels between the anchor and the panel. Defaults to `0`.                                                      |
| `offset`        | `number`                                                    | Pixels to shift the panel along the anchor's edge (below). Defaults to `0`.                                    |
| `onDismiss`     | `(reason) => void`                                          | Called with the reason the overlay asks to close (below); the caller closes the panel, or not.                 |
| `initialFocus`  | `"first"`, `"panel"`, `"none"` or an `HTMLElement`          | Where focus goes on attaching (below). Defaults to `"first"`.                                                  |
| `returnFocusTo` | `HTMLElement \| null`                                       | Where focus goes on detach. Defaults to the element focused when the overlay attached; `null` leaves it alone. |

The panel is positioned `fixed` and opens on the preferred side unless only the opposite side has room for it, lines up with the preferred edge of the anchor unless only the other edge keeps it on screen, and is pushed back inside the viewport if it still overflows. The placement it ends up with is written to `data-gridkit-placement`. Whenever the panel's own size changes — a list that shrinks under a search, content that loads in — it is placed again from the anchor's current box and the same preferred placement, so a panel flipped above its anchor keeps its bottom edge against it. An anchor taken out of the page while the panel is open — the header of a column the panel just hid — leaves it placed beside where that anchor last was.

`offset` moves the panel along the edge it lines up with: down beside a `left` or `right` side, right beside `top` or `bottom`; a negative offset goes the other way. A submenu opened `right-start` passes its own top padding, negated, so its first item lines up with the item that opened it. The edge is chosen for the shifted panel, and it is still kept on screen.

Focus moves to the panel's first focusable element (`"first"`), or to the panel itself when it has none; `"panel"` focuses the panel itself, given `tabindex="-1"` when it has no `tabindex`; `"none"` leaves focus where it was, for a popup the user keeps typing past; an element focuses that element — a filter editor's value box rather than the operator picker before it, say.

It asks to close with one of these reasons. Nothing on the anchor counts, so a button that toggles the panel closes it with its own click.

| Reason      | When                                                                                                                  |
| ----------- | --------------------------------------------------------------------------------------------------------------------- |
| `"escape"`  | <Kbd>Escape</Kbd> was pressed while it was the topmost overlay.                                                       |
| `"outside"` | A pointer went down outside it and outside every overlay above it.                                                    |
| `"scroll"`  | Something outside it scrolled — it is placed in viewport coordinates, so the anchor would move away from it.          |
| `"resize"`  | The window resized.                                                                                                   |
| `"blur"`    | The window lost focus, or focus moved somewhere outside it and outside every overlay above it.                        |
| `"parent"`  | The overlay it was opened above detached. It is detached straight after, whatever the caller does with the dismissal. |

Detaching returns focus only while focus is still in the panel, in an overlay above it, or nowhere — after a click on another control, focus stays there.

### Stacking

Overlays stack in the order they attach, so a submenu opened from a menu, or a picker opened from a filter panel, sits above the overlay it came from.

- <Kbd>Escape</Kbd> belongs to the topmost overlay alone: it is asked to close
  and the key goes no further — it is taken in the capture phase on `window`,
  before anything else on the page hears it. A grid that clears its selection on
  <Kbd>Escape</Kbd>, or a dialog that closes on it, is not disturbed by an
  <Kbd>Escape</Kbd> that closed a menu, and a second <Kbd>Escape</Kbd> closes
  the overlay below. With no overlay open, <Kbd>Escape</Kbd> passes through
  untouched.
- An overlay counts everything inside the overlays above it as inside itself: a click or a focus move into a submenu keeps its menu open, while a click elsewhere in the menu closes only the submenu, and a click outside both closes both.
- Detaching an overlay first dismisses every overlay still above it with `"parent"` and detaches it, topmost first, so a submenu never outlives its menu.

`placeOverlay(anchorRect, panelSize, viewport, { placement, gap, offset })` is the placement on its own: pure arithmetic over boxes, returning `{ top, left, placement }`, for a renderer that positions its own panels.

## Context menu trigger

`attachContextMenuTrigger(root, { onRequest })` reports every context menu the user asks for inside `root` — a right-click, <Kbd>Shift</Kbd>+<Kbd>F10</Kbd>, the <Kbd>ContextMenu</Kbd> key, or a touch held still for half a second — and returns the function that stops it. `onRequest` is called with a `ContextMenuRequest` and answers whether it opened a menu of its own: `true` prevents the browser's menu, `false` lets it show, so a part of the grid with nothing to offer keeps the browser's.

| Field    | Type                      | Description                                                                                                                  |
| -------- | ------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `target` | `Element`                 | The element under the pointer, or the focused one for a key.                                                                 |
| `point`  | `{ x, y } \| null`        | Where the pointer was, in viewport coordinates — an overlay anchor as it is. `null` from the keyboard: open beside `target`. |
| `source` | `"pointer" \| "keyboard"` | How it was asked for: a right-click or a long-press, or a key.                                                               |

```ts
import { attachContextMenuTrigger, attachOverlay } from "@gridkitjs/dom";

const stop = attachContextMenuTrigger(gridElement, {
  onRequest: ({ target, point }) => {
    const cell = target.closest("td[data-gridkit-column]");
    if (cell === null) return false; // the browser's menu, then
    showMenu(point ?? cell); // an attachOverlay anchor: the point, or the cell
    return true;
  },
});
```

Each gesture asks once. On some systems a key press also makes the browser fire a `contextmenu` event of its own; once the key opened a menu, that event is taken rather than reported again.

A long-press is a primary touch that rests for 500 ms, drifting no more than 10 pixels; one that moves further, lifts sooner or is taken over by the browser to scroll asks nothing, and a mouse or pen held down never asks. It is reported with the touch's point. A browser that turns a held touch into a `contextmenu` of its own — Chrome on Android does — asks once, whichever comes first. Once a long-press opened a menu, the click its lifting brings is taken before anything under the finger hears it: the menu opened there, and a click would land in it.

An event something already prevented is left alone, so a cell template with a menu of its own keeps it. For that, the trigger listens on the document in the bubble phase — after a framework that handles events at its root container, as React does, where a listener on `root` would hear them first — and counts only events whose target is inside `root`.

## Menu

`attachMenu(panel, options)` makes a menu the renderer has drawn behave as one, following the [WAI-ARIA menu pattern](https://www.w3.org/WAI/ARIA/apg/patterns/menubar/): keys, typeahead and the pointer move focus among its items, and choosing one is reported through callbacks. It decides what each key and hover does; the renderer runs the item, opens or closes the submenu, and draws the result. It returns `focusItem(idOrIndex)` and `detach()`.

What to show is @gridkitjs/core's: [`resolveMenu`](/docs/core/commands#menus) resolves a grid's menu entries to the items to draw, and the keys below are worked out with its [pure helpers](/docs/core/commands#keyboard). `attachMenu` reads only the markup:

| Markup                                                       | Read as                                                                                                                                             |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `role="menuitem"`, `"menuitemcheckbox"` or `"menuitemradio"` | An item, when it also carries `data-gridkit-menu-item`. Its value is the id every callback reports. Read afresh on every key, so later items count. |
| `aria-haspopup="menu"`                                       | An item that opens a submenu. Give it `aria-expanded` too, `"true"` while the submenu is open.                                                      |
| `aria-disabled="true"`                                       | A disabled item: it takes focus, so a screen reader finds it, but is never chosen.                                                                  |
| `role="separator"`, or anything else                         | Not an item, so the keys pass over it.                                                                                                              |
| `aria-label`, else the text                                  | The label typeahead matches.                                                                                                                        |

It keeps one item the tab stop — `tabindex="0"` on the focused item, or the first, `-1` on the rest — so attach the menu before its overlay, and the overlay's initial focus lands on the first item.

| Option              | Called                                                                                                                                                                                                       |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `onActivate`        | `(id)` — an enabled item that opens no submenu was chosen. Run it and close every menu.                                                                                                                      |
| `onOpenSubmenu`     | `(id, { focus })` — an enabled submenu item asks for its submenu. `focus` is `"first"` from the keyboard, so focus its first item; `"none"` from a click or the pointer resting on it, so leave focus there. |
| `onCollapseSubmenu` | `()` — the pointer came to rest on another item. Close any submenu open from this menu.                                                                                                                      |
| `onCloseSubmenu`    | `()` — <Kbd>ArrowLeft</Kbd> in this menu, which is a submenu: close it. Pass it only to a submenu's menu.                                                                                                    |
| `onClose`           | `("tab")` — <Kbd>Tab</Kbd> or <Kbd>Shift</Kbd>+<Kbd>Tab</Kbd>: close every menu, and focus returns to where the first was opened from.                                                                       |

| Key                                              | Does                                                                                                                                                        |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| <Kbd>ArrowDown</Kbd> / <Kbd>ArrowUp</Kbd>        | Focuses the next or previous item, wrapping round the ends.                                                                                                 |
| <Kbd>Home</Kbd> / <Kbd>End</Kbd>                 | Focuses the first or last item.                                                                                                                             |
| <Kbd>Enter</Kbd> / <Kbd>Space</Kbd>              | `onActivate(id)`; on a submenu item, `onOpenSubmenu(id, { focus: "first" })`. Nothing on a disabled item.                                                   |
| <Kbd>ArrowRight</Kbd>                            | On a submenu item, `onOpenSubmenu(id, { focus: "first" })` — also for one already open, when focus should move into it.                                     |
| <Kbd>ArrowLeft</Kbd>                             | `onCloseSubmenu()`, when given.                                                                                                                             |
| <Kbd>Tab</Kbd> / <Kbd>Shift</Kbd>+<Kbd>Tab</Kbd> | `onClose("tab")`, in place of the key's own move.                                                                                                           |
| A printable character                            | Typeahead: focuses the next item whose label starts with what was typed in the last half second. One letter typed again steps through every item it starts. |
| <Kbd>Escape</Kbd>                                | Not handled here: the [overlay stack](#stacking) closes the topmost overlay.                                                                                |

Moving the pointer over an item focuses it at once. What the item opens or closes waits until the pointer has rested on it for 150 ms: a submenu item reports `onOpenSubmenu(id, { focus: "none" })`, any other item `onCollapseSubmenu()`. Leaving the panel cancels the wait, so a pointer crossing another item on its way into an open submenu leaves it open. A click chooses an item as <Kbd>Enter</Kbd> does, except that a submenu opens with `focus: "none"`. Touch has no hover: only its taps count, as clicks.

### Submenus

A submenu is a menu of its own: a panel with its own `attachMenu`, shown in an overlay of its own anchored to its item. Attach it when it opens, after the menu below it, so it sits above that menu in the [stack](#stacking): <Kbd>Escape</Kbd> then closes the submenu alone, focus goes back to its item, and closing the menu closes the submenu with it.

```ts
import {
  attachMenu,
  attachOverlay,
  type AttachedMenu,
  type MenuSubmenuFocus,
} from "@gridkitjs/dom";

// <div role="menu" aria-label="Column"> holding, among its items,
// <div role="menuitem" data-gridkit-menu-item="grouping"
//      aria-haspopup="menu" aria-expanded="false">Grouping</div>
function showMenu(
  anchor: HTMLElement,
  menu: HTMLElement,
  submenu: HTMLElement,
) {
  const groupingItem = menu.querySelector<HTMLElement>(
    '[data-gridkit-menu-item="grouping"]',
  )!;
  let openSubmenu: { behaviour: AttachedMenu; close: () => void } | null = null;

  function closeSubmenu() {
    openSubmenu?.close();
  }

  function showSubmenu(focus: MenuSubmenuFocus) {
    if (openSubmenu !== null) {
      if (focus === "first") openSubmenu.behaviour.focusItem(0);
      return;
    }
    document.body.append(submenu);
    groupingItem.setAttribute("aria-expanded", "true");
    const behaviour = attachMenu(submenu, {
      onActivate: (id) => {
        run(id);
        close();
      },
      onCloseSubmenu: closeSubmenu,
      onClose: close,
    });
    const detach = attachOverlay(groupingItem, submenu, {
      placement: "right-start",
      offset: -4, // the submenu's top padding, so its first item lines up
      initialFocus: focus,
      onDismiss: closeSubmenu,
    });
    openSubmenu = {
      behaviour,
      close: () => {
        openSubmenu = null;
        detach();
        behaviour.detach();
        submenu.remove();
        groupingItem.setAttribute("aria-expanded", "false");
      },
    };
  }

  document.body.append(menu);
  const behaviour = attachMenu(menu, {
    onActivate: (id) => {
      run(id);
      close();
    },
    onOpenSubmenu: (_id, { focus }) => showSubmenu(focus),
    onCollapseSubmenu: closeSubmenu,
    onClose: close,
  });
  const detach = attachOverlay(anchor, menu, { onDismiss: close });

  function close() {
    detach(); // dismisses the submenu above it with "parent" first
    behaviour.detach();
    menu.remove();
  }
}
```

## Toolbar

`attachToolbar(toolbar)` makes a `role="toolbar"` element the renderer has drawn one tab stop that the arrow keys move within, following the [WAI-ARIA toolbar pattern](https://www.w3.org/WAI/ARIA/apg/patterns/toolbar/), and returns the function that stops it. What the toolbar lists is @gridkitjs/core's: [`resolveToolbar`](/docs/core/toolbar#resolving) resolves a grid's toolbar entries to the items to draw.

| Markup                      | Read as                                                                                                                                                                                                      |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `data-gridkit-toolbar-item` | An entry, holding the item's `key`. Its control is the entry itself when it can take focus, else the first element in it that can — a search box's input, a custom entry's button. Read afresh on every key. |
| An entry with no control    | A separator or a spacer: the keys pass over it.                                                                                                                                                              |
| `aria-disabled="true"`      | A disabled control: it still takes focus, so a screen reader finds it. Running it is the renderer's to refuse.                                                                                               |

One control at a time has `tabindex="0"` — the focused one, or the first — and the rest `-1`, so <Kbd>Tab</Kbd> reaches the toolbar once and returns to the control last used. A control drawn later, such as a button whose command became visible, joins with `-1`, leaving the tab stop where it was. Leave `tabindex` to it.

| Key                                          | Does                                                           |
| -------------------------------------------- | -------------------------------------------------------------- |
| <Kbd>ArrowRight</Kbd> / <Kbd>ArrowLeft</Kbd> | Focuses the next or previous control, wrapping round the ends. |
| <Kbd>Home</Kbd> / <Kbd>End</Kbd>             | Focuses the first or last control.                             |

A text field keeps the keys it needs: <Kbd>Home</Kbd> and <Kbd>End</Kbd> move its caret, and so do the arrows while there is text to move through. With the caret at the start, <Kbd>ArrowLeft</Kbd> moves on to the previous control; at the end, <Kbd>ArrowRight</Kbd> to the next — otherwise a search box holding the tab stop would leave no way to the controls after it. With text selected, or in a field that keeps its caret to itself, such as `type="email"`, the arrows stay with the field.

```ts
import { attachToolbar } from "@gridkitjs/dom";

// <div role="toolbar" aria-label="Grid toolbar">
//   <div data-gridkit-toolbar-item="search"><input type="search" … /></div>
//   <div data-gridkit-toolbar-item="spacer-1"></div>
//   <button data-gridkit-toolbar-item="filter.clearAll" aria-disabled="true">Clear filters</button>
// </div>
const detach = attachToolbar(toolbarElement);
```

### Overflow

`observeToolbarOverflow(toolbar, { items, onChange })` measures how many of a toolbar's entries fit in it, and reports the count — what @gridkitjs/core's [`fitToolbarItems`](/docs/core/toolbar#overflow) works out from the widths — through `onChange`: once straight away, so a renderer calling it before paint draws the right entries from the first frame, and again whenever it changes. Draw the first `count` entries and every pinned one — or let [`splitToolbarItems`](/docs/core/toolbar#overflow) split them — and put the rest in a "More" menu button at the end. It returns `update(options)` and `detach()`.

| Option     | Type                             | Description                                                                                        |
| ---------- | -------------------------------- | -------------------------------------------------------------------------------------------------- |
| `items`    | `readonly ToolbarOverflowItem[]` | Every entry, drawn or in "More", in order: `{ type, key }`, as `resolveToolbar`'s items have them. |
| `onChange` | `(count) => void`                | How many entries fit, from the start. Called straight away, then only when it changes.             |

| Markup                      | Read as                                                                        |
| --------------------------- | ------------------------------------------------------------------------------ |
| `data-gridkit-toolbar-item` | An entry, whose value is its item's `key`.                                     |
| `data-gridkit-toolbar-more` | The "More" button — an entry too, for `attachToolbar`, but not one of `items`. |

An entry moved into "More" is no longer drawn, so its width is remembered by key from the last time it was. One never drawn yet counts as nothing: it is drawn, measured, and moved back out if it does not fit. The "More" button likewise counts as nothing until it is first drawn. A spacer counts as nothing too, since its width is only the room left over. The toolbar's padding and the `column-gap` between entries are allowed for, so a theme can space them however it likes.

It measures again whenever the toolbar or an entry resizes, and whenever entries are drawn or taken away — those the count it reported lets in, or the "More" button — so the renderer only draws what it is told. When the items change, pass them to `update`.

```ts
import { resolveToolbar, splitToolbarItems } from "@gridkitjs/core";
import { observeToolbarOverflow } from "@gridkitjs/dom";

const overflow = observeToolbarOverflow(toolbarElement, {
  items,
  onChange: (count) => draw(splitToolbarItems(items, count)), // { shown, overflow }
});

// when the grid changes:
items = resolveToolbar(entries, { commands, contextFor });
overflow.update({
  items,
  onChange: (count) => draw(splitToolbarItems(items, count)),
});
```
